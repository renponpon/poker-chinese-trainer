# Roadmap

最終更新: 2026-09-07

## 9月7日確定条件と実地検証の実行手順

ユーザー合意：翻訳・解説・音声APIの予算は月3,000円。中国・マカオ・香港・台湾などで中国語、英語を生活で使う地域で英語を対象とし、言語による優先度は付けない。以下は準備済みの運用設計であり、募集開始・設定反映・実地検証の完了記録ではない。

### 対象と検証範囲

同じ条件で両言語を募集する。「最近1週間に言えなかった一言がある」「今後も同じような会話がある」「次は自分で言いたい」海外在住の日本人を対象にする。生活上の買い物・配達・近所付き合い・職場の雑談などを入口にし、国内レッスン受講生へ対象を移さない。

現実装の中国語は `zh-CN` の音声と `zh-Hans` のAzure訳、英語は `en-US` の音声・DeepL訳を使う。地域別設定や広東語、繁体字選択は現時点でない。「英中同優先」は品質・地域適合が既に同一という判定ではない。

| 対象地域 | 共通テストに加える確認 | 紹介時の範囲 |
|---|---|---|
| 中国本土 | 現地の普段の回線でサイト、ログイン、翻訳3モード、音声、同期を個別に確認 | 日本側の成功を本土接続の証明としない。動いた回線・地域だけ記録 |
| マカオ・香港 | 実際に普通話を使う相手・場面か、読み上げとピンインが用途に合うか | 中国語は普通話中心と説明し、広東語対応とは案内しない |
| 台湾 | 簡体字の表示が利用の妨げになるか、普通話の語彙・発音が意図に合うか | 繁体字選択・台湾向け表現最適化を実装済みとしない |
| 英語を生活で使う地域 | 現地の相手へ意味・丁寧さが合うか、音声入力・読み上げが使えるか | 米語設定と地域別の言い方を区別する |

国だけで利用言語を決めつけず、本人が使う相手と言語で判定する。全地域の確認が揃うまで待つ必要はないが、未確認地域を動作確認済みとして募集しない。Webからの翻訳はサーバー経由なので、外部翻訳サイトの直接接続可否だけでPhrabitの動作を断定しない。

### 月3,000円の扱いと設定案

本番・Preview・開発者テスト・再生成・解説・高精度音声のPhrabit分を合算する。API契約の固定料金と税も含め、Vercel・DB・ドメイン・広告費は別管理とする。既に使った今月分を含む上限で、新たに3,000円追加できる意味ではない。9月7日現在、当月の実請求・契約プラン・他アプリとの課金共有は未確認。

運用目安は合計1,500円で確認、2,100円で新たな配信拡大と任意の大量APIテストを保留、2,400円で有料生成停止の判断。残り600円は請求反映の遅れ・税・為替の余裕とする。これは設定案であり、自動通知・停止を設定済みではなく、超過しない保証にもならない。

| 提供元 / 現在の用途 | 用意した設定手順 | 未確認事項 |
|---|---|---|
| Gemini / 品質訳・調整・解説・例文 | Phrabitの課金プロジェクトを照合し、単一プロジェクト・Gemini API対象のSpend capの利用可否を確認。通知用budgetと停止用capを区別 | 対象プロジェクト、今月分、無料/有料区分、設定可能額・機能 |
| DeepL / 通常訳 | Account → API Keys & Limitsで契約と現在利用量を確認。利用可能なら契約Cost ControlまたはPhrabitキーの文字数上限を設定 | 現契約の固定料金、従量単価、共有キーの有無 |
| Azure / 速度訳・通常訳失敗時 | 対象TranslatorリソースのSKU・使用量を確認し、Cost Managementの通知を用意。通知だけを強制停止として扱わない | 無料枠/有料SKU、Phrabit専用か、停止可能な単位 |
| OpenAI / 高精度音声入力・読み上げ | Phrabit Project → Limits → Spendで月額とEnforce a hard limitを確認。組織全体で他アプリを止めない | 課金プロジェクト、今月分、通貨、共有利用、既存上限 |

各社の上限は合計が2,400円相当以内になるよう、当月の既使用額と固定料金を確認後に割り当てる。外貨額は設定時の換算根拠と税を記録する。固定料金だけで収まらない場合は契約変更案を本人へ提示し、黙って解約・更新しない。DeepL停止後にAzureへ切り替わる費用、停止エラーの再試行も考慮する。月額API上限を利用者一人あたりの日次回数へ機械的に置き換えない。

設定時の記録欄：`提供元 / 課金対象名 / Phrabit専用か / 請求期間 / 既使用額 / 固定料金 / 上限と通貨 / 通知のみor停止 / 設定確認日時`。キー値や決済情報は記録しない。実請求の確認前に「1人あたり何円」「何人まで使える」を確定しない。既存イベントはトークン数・音声出力時間を網羅しておらず、リクエスト件数だけから正確な費用は算出できない。

公式資料を2026-09-07確認：Googleの[Spend cap（Preview）](https://docs.cloud.google.com/billing/docs/how-to/budgets-spend-caps)は対象サービス・プロジェクト単位。DeepLの[Cost Control](https://developers.deepl.com/docs/best-practices/cost-control)は到達後の処理を停止。Azureの[Budget](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets)はそれ単独では利用を停止しない。OpenAIの[Spend limits](https://developers.openai.com/api/docs/guides/spend-limits)は強制停止設定があるが伝播は即時ではなく超過の可能性がある。各アカウントに設定済みであることとは区別する。

スマホ確認は両端末で一度再読込し、同じ本番アカウント・同じ学習言語で行う。スマホで自分の一言を翻訳→「ドリルに追加」→表示中のPCへ約30秒で反映、スマホで回答→PCでも学習状態更新、通信断中に保存済みの一言へ回答→復帰後に同期、の3操作。新しい翻訳のオフライン生成は試験対象外。ログアウト・ブラウザデータ削除はしない。エラー時は直前操作・地域/回線・時刻を記録する。

### 紹介先への依頼と7日間

紹介候補と公開窓口は `segment-marketing-experiment-2026-07.md`、そのまま確認できる依頼文は `beachhead-outreach-templates.md` の9月7日節に用意した。英中それぞれ最初に2件の紹介先へ打診する作業目標。未確認の窓口は確認してから送信する。本人の宛先・文面承認後に送信し、紹介先には教材作成・毎日の督促・個人情報リストの提供を依頼しない。

実利用者は最初の30人（英中各15人を目安）を目指すが、人数が揃うのを待たず各人の初回利用日から観察する。1人ずつ面談を積み重ねる方式には戻さず、紹介先の既存案内・コミュニティで一度共有してもらう。

| タイミング | 利用者への案内 | 運営が見ること |
|---|---|---|
| 初回 | 「最近、現地で言えなかった一言を入れて、覚えたいと思ったら追加してください」 | 流入→翻訳成功→追加。不要な追加やドリルを義務にしない |
| 初回後 | 任意でその一言のドリルを案内 | 操作テストとして促した回答と自然な利用を分ける |
| 1〜6日後 | 毎日の督促はせず、生活で必要なときに利用 | 別日の回答と、新しい会話後の追加。期間途中で案内や価格を大きく変えない |
| 7日後 | 連絡了承者に1回だけ短い確認 | 再利用しなかった理由、次の会話で使えたか、追加は自発的だったか |

記録単位は `紹介元ref / 対象言語 / 初回利用日 / 訪問者 / 翻訳成功者 / 追加成功者 / 別日の回答者 / 別日の追加者 / 自発追加の本人確認 / 実会話で使えた本人確認 / 不具合 / API実費`。人数とイベント回数を分ける。`translation_drill_save`のsuccess=trueを追加に数え、sync_failedは同期課題として別記。ゲストの識別は同一ブラウザ単位で、別端末を同一人物と断定しない。テスト用ref、開発者・身内の検証操作を獲得成果から除外する。refは紹介元を示すだけで、本人の所在地や学習言語を自動設定するものではない。

判定は両言語で同じ基準にする。初回利用者30人中、7日以内の別日利用10人を仮目安として維持する。繰り返す生活場面から自発追加が複数人で出れば拡大候補。訪問がないなら紹介導線、翻訳後に追加されないなら保存価値・翻訳品質、追加後に別日利用がないなら復習の理由と再発場面を確認する。7日経過していない人は7日指標の分母から外し、母数不足・計測欠損を需要ゼロと扱わない。件数差だけで片方の言語を打ち切らない。

### 運営用の品質確認セット

下記は期待する意味を定義したテスト入力であり、API生成結果ではない。利用者に10問の提出は求めない。9月7日の実API10件の結果をまず再利用し、追加実行は既知不具合を直した箇所・現地接続確認へ絞る。

| 入力・調整例 | 両言語で維持すべき意味 |
|---|---|
| 明日ではなく、明後日の午前中に来てください | 否定先・日付・午前中 |
| 二つのうち、一つだけ持ち帰ります | 二つ全部ではなく一つ |
| 彼に渡すのではなく、私に返してください | 渡す相手と返却先。中国語の还の読み |
| 辛くしないでください。でも香辛料は入れて大丈夫です | 辛さと香辛料全体の禁止を混同しない |
| 受け取ったら、私に知らせてください | 受領後という順序・連絡先 |
| ここに置いてもいいですか | 許可の質問。命令にしない |
| まだ届いていません | 否定・未完了。紛失と断定しない |
| 静かにしてください → もっと強い命令にして | 調整で語調を変更し、意味や対象を増やさない |
| 全てのチップ → ポーカーのチップの意味です | 名詞句を維持し、賭ける・支払う行動を追加しない |
| また来週、同じ時間でお願いします | 翌週・同時刻。曜日を創作しない |

主訳・読み・解説の一貫性、3モードの成功、主訳が見えるまでの時間と後続解説の時間を分けて記録する。同じ端末/回線で比較し、品質改善のための追加LLMレビューを待ち時間に入れない。

## 9月の実行計画（以下の旧フェーズより優先）

海外生活者を対象に、基本無料のまま「現地で訳す→覚えたい一言を追加→別日に復習→次の生活場面で自発追加」を成立させる。国内レッスン向けへの転換は行わない。

### 最初の30日

| 順序 | 作業 | 完了条件 |
|---|---|---|
| 1 | 未公開のニュアンス調整・確認後追加フローを検証 | 未追加時に保存されない、失敗時の元訳維持、追加時の保存と重複防止を確認。実API・海外接続・同期は代替テストと区別 |
| 2 | 海外生活者向けの案内・紹介依頼・候補を準備 | 宛先、対象との適合、送信文が具体的で承認可能。動画は動作確認後に実画面で作成 |
| 3 | 許可を得た紹介元から案内 | 20件提案・3件紹介・身内以外30人初回利用を作業目標とする。実施前の数値を実績にしない |
| 4 | 生活での反復と原価を確認 | 保存・別日の復習・新規追加を紹介元別に人数で確認。API実費と作業時間も記録 |
| 5 | 継続利用者向けの有料追加枠を具体化 | 無料枠、追加枠、価格、原価の根拠を用意してから価格提示を承認に出す |

原価集計では、既存の利用イベントから機能・provider・モード・入力文字数・利用者を確認し、実請求と突き合わせる。トークン数など未取得の項目を推測で実測値にしない。解説・音声・再調整と無料利用者の原価を含める。

基本無料は無制限生成を意味しない。生成回数の追加枠が最初の有料候補で、月980円は未決定の仮説。保存済みデータの閲覧・復習・同期を突然課金で遮断しない。基本機能の無料体験が期限切れになる案は採用しない。

初回利用30人から翌週も利用する10人を仮の検証目安にする。支払い検証が可能になった段階で購入5人、さらに翌月更新3人を目安とする。30日以内に有料化を強制せず、無料価値・有料需要・利益を分けて判定する。少数の購入だけで事業成立と断定しない。

### 実施状況（2026-09-05）

- 方針と紹介用文面を更新。現地の紹介候補3件を公式サイトで確認して記録。教室への営業送信、提携、価格公開は未実施。
- ニュアンス調整と確認後追加はローカル実装済み・未公開。実翻訳APIはローカルキー未設定のため未検証。
- 画面回帰テストで再調整中の別送信が可能な不備を再現し修正。中国語390px・英語430pxで未追加時の非保存、調整失敗時の元訳保持、明示追加、同期失敗時のローカル保持を確認。API応答固定であり実翻訳・実同期の証明ではない。
- 未追加候補の一時保存は次の実装候補で、まだ実装済みとして告知しない。
- Xは補助媒体。これまでのオンラインレッスン層向け検索だけに獲得作業を集中させない。予定済みタスクの設定変更は別途確認する。

## 現在フェーズ

現在は、ポーカー向け初期告知で継続利用がほぼ残らなかった結果を受け、Phrabit の中心価値がどの利用場面で成立するかを比較する顧客セグメント発見フェーズです。

優先すること:

- セグメント別の告知・返信・流入元を分ける
- フレーズ入力・保存・ドリル・再訪の行動を見る
- 実会話やレッスン後の自発的な追加登録を最重要シグナルにする
- 実際に使った人に限り、短いフォローアップで理由を確認する
- 明確なバグや小さな摩擦だけ直す

優先しないこと:

- 大規模リファクタ
- スコープ外の新機能
- 反応が確認できていないセグメント向けの多機能化
- 検証前の課金機能作り込み
- 最初から少人数インタビューだけに戻ること
- 講師・法人・学校向け機能の先行開発

## 直近30日

目的:

海外生活、留学・ワーホリ、オンライン語学レッスン・言語交換、海外業務、接客のうち、どの利用場面で保存・ドリル・再訪が自然に起きるかを見る。

やること:

1. セグメント別の投稿文と `ref` 付きURLで告知する
2. Xでは普通の学習者・現地で困っている人を中心に、役立つ返信から接触する
3. フレーズ入力、保存、ドリル開始、D1/D7再訪をセグメント別に確認する
4. 実会話やレッスン後に新しいフレーズが自発的に追加されたか確認する
5. 実利用が発生した人だけ、負担の小さい短いフォローアップを行う
6. 上位1〜2セグメントを選び、その層にだけ訴求と導線を寄せる
7. 明確なUI摩擦とバグだけ小さく直す

判断ポイント:

- どの層が「便利そう」ではなく実際にフレーズを入力するか
- 保存したいフレーズが自発的に選ばれるか
- ドリル対象の選択が自然か
- 翌日以降の再訪と追加登録が起きるか
- 同じ利用場面から複数人の具体例が出るか

### 仮の判定ライン

セグメント別の告知実験用の仮置きです。Xの反応率だけで判断せず、実利用人数・具体的な入力内容・再訪を合わせて見ます。

| 指標 | 最低ライン | 強いシグナル |
|------|------------|--------------|
| フレーズ入力者 | 1セグメントで5人以上 | 複数投稿から継続的に入力者が出る |
| 保存 | 1セグメントで2人以上 | 入力者の半数以上が保存する |
| ドリル開始 | 1セグメントで1人以上 | 保存者の半数以上がドリルを始める |
| D1再訪 | 1セグメントで1人以上 | 再訪後に新しい保存・ドリルが起きる |
| D7再訪 | 1セグメントで1人以上 | 同じ利用場面で継続利用が起きる |
| 会話後の自発追加 | 1セグメントで1人以上 | 複数人が実会話・レッスン後に繰り返し追加する |
| 具体的な困りごと | 同一セグメントで3場面以上 | 同じ課題構造が複数人から自然に出る |

このラインを下回った場合も即失敗とはしない。使われなかった場面、保存されなかった理由、既存解で十分だった理由を `docs/open-questions.md` に戻して、次の検証設計を修正する。

- `ref` 別の入力・保存・ドリル・再訪確認

- 保存・ドリル追加が自発的に起きる
- D1/D7 の再訪が一部でも起きる
- 実会話後に新しいフレーズ追加が起きる
- 既存翻訳ではなくPhrabitを開く理由が具体化する

## Phase 3: 継続価値と課金価値の検証

目的:

勝ちセグメントで利用の反復を強め、無料利用を超えて支払い意思につながるかを確認する。

主要タスク:

- 支払い意思のインタビュー
- 価格帯の仮説作成
- 会話・レッスン後に戻る導線の改善
- 初回フレーズ作成から最初のドリルまでの摩擦改善
- 無料/登録不要からログイン・課金へつなぐ導線の検討
- 高精度/仕事モードの価値確認

確認する問い:

- 何に対して払うのか
- 月額か買い切りか
- 個人課金か会社経費か
- ポーカー層と業務層で価格許容が違うか

根拠:

- `docs/roadmap-2026-2028.md`
- `docs/open-questions.md`
- `docs/translation-provider-evaluation.md`
