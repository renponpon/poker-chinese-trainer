# 次イテレーション 実装候補の切り分け

## 2026-09-06 追記：共通の学習言語

下記レビューには概ね合意。追加の優先課題として、英語利用者が毎回中国語から変更しなくて済むよう、翻訳・ドリル・保存・会話の学習言語を一つに統一した。メニューまたは各画面で選び、同じブラウザの次回利用・別タブへ反映する。画面別設定や言語変更に伴う追加生成は設けない。ローカル実装済み・未公開で、アカウントを介した別端末への設定同期は含まない。

### 同日の実装状況

合意したA1〜C1の最小セットもローカル実装した。端末保存と解説を分離し、未同期差分の保持・再試行、未選択会話の非永続化、任意サンプル、追加した一言からの直接練習、主要操作優先の配置、同一タブの直前訳復元を対応した。保存後の本文修正や新しいAI機能は追加していない。

単体87件・疑似クラウド同期・固定APIの画面スモークで検証。実アカウントの複数端末や海外回線、実翻訳品質・生成時間は未検証であり、本番反映前に残る確認事項。サーバー側の完全同時更新競合や初回統合前の削除履歴を全面解決したとは扱わない。実装詳細は `handoff-codex.md` の9月6日節を参照。コミット・デプロイは未実施。

## 2026-09-06：Astraによる顧客視点レビュー（以下は改修前の根拠と提案）

### 判断と確認範囲

海外生活で現地語を繰り返し使い、次は自分で言いたい日本人を対象に、既存の顧客観察・実装をAstraでレビューした。あわせて改修前のローカル画面を390px幅で操作した。翻訳APIは固定レスポンスのため、翻訳品質・実クラウド同期・海外通信はこのレビューで検証していない。本節は改修前の記録であり、実装状況は直前の節を参照する。

中核機能は概ね揃っている。追加機能の数よりも、**自分が言えなかった一言を、安心して残し、次に自分で言う練習へつなげる**設計を優先する。「最善」や継続利用への効果は、実地利用を経ないと断定できない。

理想の最短経路：言えなかった一言を入力 → 翻訳 → 必要な場合だけニュアンス調整 → 選んで保存 → その一言を練習 → 次の現場で使う。

### 最小改修セット

|---|---|---|---|

### 維持・後回し

- 維持：無料の基本フロー、明示的なドリル追加、任意の自由文ニュアンス調整、音声、ピンイン、長い解説、検索、SRS、ログイン同期。解説本文を短くする提案ではない。
- 条件付き候補：保存後の本文・ニュアンス修正。同じIDで更新し、ピンイン・解説・同期・学習履歴を整合させる必要があるため負担は中。現場で訂正された後に困る頻度を確認し、最小セットの後に判断する。
- 後回し：AI会話、発音採点、独立したリスニングドリル、OCR、共有教材、講師管理、複雑な整理・習慣化機能。必要性を確認する前に先行開発しない。
- 通常の生成呼び出し回数、必須入力、確認操作を増やさない。学習意欲の低さまで新機能だけで解決できるとは扱わない。

### 改修の完了条件と打ち切り

1. 選んだ翻訳が一度だけ保存され、解説待ちや解説失敗でも保存・練習が妨げられない。
2. 実際の同期失敗・再読込・再試行・複数端末で、消失・重複・削除復活・アカウント間混在がないことを検証する。
3. 追加した自分の一言から練習を始められ、サンプル練習を本人のフレーズ学習実績に混ぜない。
4. 画面移動で直前の結果が消えず、未選択会話の永続保存に依存しない。
5. 長い解説より前に主要操作へ到達でき、生成時間・必須入力・確認の負担を増やさない。

この最小セットを終えたら機能開発をいったん区切り、既存ロードマップに戻る。海外生活の実際の一言について、保存→別日の復習→現場で再利用→自発的な追加が起きるかを確かめる。以後の開発は、繰り返し観測した障害を優先する。

## 0. 第三フェーズでの考え方

添付画像の第三フェーズは、実装を完成させる段階ではなく、**製品コンセプトを顧客の現実に当てて検証し、洗練する段階**。

そのため、次イテレーションの実装判断は「欲しいと言われた順」ではなく、次の問いに答えられるかで切る。

1. この製品は、顧客が重要だと思っている課題を解決しているか
2. 顧客は既存の解決策から乗り換える理由を感じるか
3. 顧客は会話中/現場で実際に使いそうか
4. 顧客は保存・整理・ドリル化に価値を感じるか
5. 価格・チャネル・購入プロセスの仮説を聞ける状態か

つまり、今作るべきものは「完成版」ではなく、**顧客の反応を引き出せる実用品に近いプロトタイプ**。

## 3. P0: 今すぐ実装する候補

P0の目的は、次の検証問いに答えること。

> 中→日を含む会話補助から保存され、全件ライブラリで見返せて、覚えたいものだけ状況別に整理/ドリル化できると、Google翻訳ではなくこのアプリを使う理由になるか。

### P0-1. フレーズデータ構造の拡張

#### 目的

現場翻訳ログ、保存済みフレーズ、ドリル対象を同じデータで扱えるようにする。

#### 実装イメージ

`Phrase` に以下を追加する。

```ts
type PhraseDirection = "ja-to-zh" | "zh-to-ja";

type Phrase = {
  id: string;
  japanese: string;
  chinese: string;
  pinyin: string;
  explanation: string;
  audioUrl: string | null;
  createdAt: string;
  direction?: PhraseDirection;
  categoryId?: string | null;
  shouldDrill?: boolean;
  source?: "manual" | "conversation" | "prototype";
  usedAt?: string | null;
};
```

#### 判定

**今すぐ。**

理由:

- 後続の全件ライブラリ/ドリル分離/カテゴリがすべてここに依存する
- localStorageの既存データは `direction: "ja-to-zh"`、`shouldDrill: true` として移行すればよい

#### 注意

- 既存ユーザーの保存データを壊さない
- Notion側スキーマがある場合は、後で合わせる。まずローカル優先でよい

---

### P0-2. 全件ライブラリとドリル対象の分離

#### 目的

「保存したものは全部残る」が、「全部を覚えさせられる」状態を避ける。

#### 実装イメージ

- ライブラリには `Phrase` を全件表示
- ドリル画面は `shouldDrill === true` のものだけ出す
- 新規保存時に `shouldDrill` を選べる
- 既存フレーズは互換性のため `shouldDrill: true` 扱い

#### 判定

**今すぐ。**

理由:

- 006の反証に対応するため必須
- 未学習溜まり問題を避ける土台
- 第三フェーズで「全部ドリルは重いか」を実地確認できる

#### 検証質問

```
翻訳したものが全部ドリルに入るのと、覚えたいものだけ選ぶのだと、どちらが続きそうですか？
```

---

### P0-3. 中国語→日本語のテキスト翻訳

#### 目的

中→日ニーズを最小コストで検証する。

#### 実装イメージ

- 追加画面または新しい翻訳画面に方向切替を置く
- `日本語→中国語`
- `中国語→日本語`
- 中→日の場合も、保存データには以下を持つ
  - `chinese`: 入力または整形後の中国語
  - `japanese`: 日本語訳
  - `pinyin`: 中国語のピンイン
  - `explanation`: 語句/ニュアンス/使う場面

#### 判定

**今すぐ。**

理由:

- 003/005/006/007/FBで独立して出ている
- 会話補助が入口になる仮説の中心
- 音声入力より先に、テキストで価値検証できる

#### 注意

- Google翻訳の完全代替を目指さない
- まずは「保存・整理・ドリル化につながる中→日」として検証する

---

### P0-4. 保存時の「ライブラリのみ / ドリルにも追加」選択

#### 目的

会話補助と学習資産化を分離しつつ接続する。

#### 実装イメージ

翻訳結果表示後に2つの主要アクションを出す。

- `ライブラリに保存`
- `ドリルにも追加`

または保存フォームでチェック:

- `あとで見返す`
- `練習したい`

#### 判定

**今すぐ。**

理由:

- 「翻訳で終わらない」が差別化
- ただし全自動ドリル化は重い
- 顧客に「この表現は覚えたい/覚えなくていい」を選ばせられる

---

### P0-5. 状況別カテゴリ/タグの手動付与

#### 目的

現地FBの「全件ライブラリを残しつつ任意フォルダ分け」を検証する。

#### 実装イメージ

最初はフォルダではなく、軽量な `categoryId` で十分。

初期カテゴリ:

- ポーカー卓
- フロア/手続き
- レストラン
- 移動
- ホテル
- 買い物
- 仕事
- 病院
- その他

ユーザー追加カテゴリは、今回は必須ではない。  
ただし、UI上は `その他` または自由入力を1つ用意できるとよい。

#### 判定

**今すぐ。ただし最小実装。**

理由:

- 現地実使用者からの明示FB
- ライブラリが増えた後の探索性に直結
- ポーカー/生活/仕事のセグメント差を確認できる

#### 注意

- 自動分類は今回は不要
- 高度なフォルダ管理UIも不要
- まず「カテゴリがあると見返しやすいか」を見る

---

### P0-6. ライブラリのカテゴリ絞り込み

#### 目的

カテゴリ保存が実際に使える体験になるかを確認する。

#### 実装イメージ

既存のSRSステータスフィルタに加えて、カテゴリフィルタを追加する。

- 全て
- ポーカー卓
- フロア/手続き
- レストラン
- 移動
- その他

#### 判定

**今すぐ。**

理由:

- カテゴリは保存だけでは意味がなく、探せて初めて価値が出る
- 実装コストは比較的低い

## 4. P1: 次に実装する候補

### P1-1. 中国語→日本語の音声入力

#### 判定

**できれば今回。ただしP0完了後。**

理由:

- ニーズは強い
- 会話中に使うには音声が重要
- ただしWeb Speech APIは環境依存があり、LINEブラウザ/中国本土で失敗例あり

- 失敗時の手入力導線を明確にする

成功基準:

- 現地ユーザーが標準ブラウザで使える
- 音声認識エラー時に離脱しない
